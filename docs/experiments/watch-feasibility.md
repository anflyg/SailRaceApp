# Watch feasibility experiment

Debug-only spike related to [PR #80](https://github.com/anflyg/SailRaceApp/pull/80). This is not a Watch product or a race-start path. The watch derives remaining time from system uptime and requests a click at 5–1 and a success haptic at zero only when its timer callback runs promptly. No background runtime is requested; missed cues are not replayed. Haptics and runtime behavior require physical testing.

The iPhone activates the WatchConnectivity receiver only in a Debug simulator build explicitly compiled with `WATCH_FEASIBILITY`. A validated, random test ID is emitted to the Capacitor `watchTest` listener in the existing guarded native-test web app; the receiver replies `processed: true` only after JavaScript calls `confirm` for that pending ID. A missing listener, invalid message, duplicate pending ID or five-second timeout yields no successful acknowledgement. Native receipt is logged without payloads; this does not record a race. No queued command is used. The native-test asset guard blocks release/archive/distribution.

## Simulator procedure

From this worktree run `npm ci`, `npm run build`, `npx --no-install cap sync ios`, then `npm run cap:copy:native-test`. Build the `WatchFeasibility` scheme for watchOS Simulator Debug unsigned first. Build the `App` scheme for iOS Simulator Debug with `CODE_SIGNING_ALLOWED=NO SKIP_INSTALL=YES` and environment variables `TACKWISE_NATIVE_TEST_BUILD=1 TACKWISE_WATCH_FEASIBILITY=1`, plus build setting `SWIFT_ACTIVE_COMPILATION_CONDITIONS="DEBUG WATCH_FEASIBILITY"`, using the same derived-data path. The latter opt-in embeds the separately built simulator Watch app. Neither the listener nor the Watch app is embedded by an ordinary Release build. The experiment does not configure provisioning, and this embedding mechanism is simulator-only.

The native-test screen can disable its Watch listener to test the timeout. For repeatable simulator-only runs, launch Watch with `--watch-auto-countdown` and/or `--watch-auto-send`; launch iPhone with `--watch-no-listener` to withhold the JavaScript listener. The countdown requests and message outcomes are logged without message payloads. These options do not exist in release or physical-device execution.

## Simulator evidence (2026-11-18)

Xcode 27.2, paired iPhone 17 Pro simulator (iOS 26.5) and Apple Watch Series 12 simulator (watchOS 27.2): simulator launch arguments invoked the same countdown and send methods as the Watch buttons; direct button interaction was not tested because the Simulator UI was unavailable to computer control. The 60-second timer displayed 00:55 and 00:31 and logged requests at 5, 4, 3, 2, 1 and 0 at one-second intervals. The display dimmed by completion, so the full 00:00 screen was not verified. Native receipt preceded the JavaScript confirmation and Watch's `JS processed` status. With the JS listener withheld, native receipt timed out and Watch reported the negative result. This is simulator evidence only, not proof of physical haptic delivery or locked/background/force-quit behavior.

Unsigned ordinary Debug and Release iPhone simulator builds with production web assets passed; neither binary contained the receiver or plugin symbols, and Release contained no Watch experiment bundle. Focused existing timer, race-logger and native-test suites passed 51 tests. The Watch and opted-in iPhone simulator builds also passed.

## Isolated internal TestFlight candidate (prepared, not distributed)

The owner approved preparation only. The shared `WatchTest` scheme archives the separate iPhone target `com.anflyg.sailraceapp.watchtest` and embedded Watch target `com.anflyg.sailraceapp.watchtest.watchkitapp`, both displayed as **TackWise Watch Test**. The Watch target's minimum is watchOS 10, compatible with the reported watchOS 26.6. The production target, bundle ID, signing, entitlements, web assets and recording flow are unchanged. The candidate has no race, GPS, account, HealthKit, workout or background execution functionality; it sends only a random test identifier. Its receiver is compiled with `WATCH_TEST_CANDIDATE` only in the separate targets; the ordinary app keeps its simulator-only Debug flag. The test listener can be disabled to demonstrate timeout.

The candidate's isolated web entry point is `watch-test/`; it imports Capacitor only. `scripts/build-watch-test-assets.sh` builds these assets into derived data and copies them into the candidate bundle. It rejects `TACKWISE_NATIVE_TEST_BUILD=1`; the existing synthetic native-test asset guard remains unchanged. The existing Xcode Cloud post-clone hook prepares production web assets and dependencies, but the candidate target does not embed the production web bundle or synthetic worker controls. Its own build phase produces the candidate assets. No Xcode Cloud workflow or App Store Connect record is configured by this change.

### Build and release gates

After `npm ci`, build locally using `xcodebuild -project ios/App/App.xcodeproj -scheme WatchTest -configuration Release -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build`. For structural validation only, use `-destination 'generic/platform=iOS' -archivePath <temporary-path> CODE_SIGNING_ALLOWED=NO archive`; this archive is unsigned and cannot be distributed. Confirm its iPhone app contains `Watch/WatchTest Watch.app` and that the companion identifier matches.

Before any signed archive or distribution, the owner must separately approve: Apple Developer registration of both test App IDs and the necessary distribution signing/profiles; creation of a separate App Store Connect app record; and configuration/activation of a manually triggered Xcode Cloud workflow using this shared scheme. The owner must then explicitly approve any upload and selection of **TestFlight Internal Only**, and internal tester access. The scheme itself does not enforce that distribution choice. Do not create certificates, profiles, records or workflows, upload, or distribute on the basis of preparation approval. Apple's internal-only distribution option is described at https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases .

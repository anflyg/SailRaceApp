# Watch feasibility experiment

Feasibility spike related to [PR #80](https://github.com/anflyg/SailRaceApp/pull/80). This is not a Watch product or a race-start path. The watch derives remaining time from a continuous monotonic deadline and requests a click at 5–1 and a success haptic at zero only when its timer callback runs promptly. The isolated Watch Test candidate also preloads a 150 ms beep at 5–1 and a 650 ms beep at zero, using the same pitch and timbre. Haptics remain enabled independently of the sound toggle. Missed cues are not replayed; cancelling stops the countdown and later cues. A user-started sailing workout requests workout background runtime.

The iPhone activates the WatchConnectivity receiver only in a Debug simulator build explicitly compiled with `WATCH_FEASIBILITY`. A validated, random test ID is emitted to the Capacitor `watchTest` listener in the existing guarded native-test web app; the receiver replies `processed: true` only after JavaScript calls `confirm` for that pending ID. A missing listener, invalid message, duplicate pending ID or five-second timeout yields no successful acknowledgement. Native receipt is logged without payloads; this does not record a race. No queued command is used. The native-test asset guard blocks release/archive/distribution.

## Simulator procedure

From this worktree run `npm ci`, `npm run build`, `npx --no-install cap sync ios`, then `npm run cap:copy:native-test`. Build the `WatchFeasibility` scheme for watchOS Simulator Debug unsigned first. Build the `App` scheme for iOS Simulator Debug with `CODE_SIGNING_ALLOWED=NO SKIP_INSTALL=YES` and environment variables `TACKWISE_NATIVE_TEST_BUILD=1 TACKWISE_WATCH_FEASIBILITY=1`, plus build setting `SWIFT_ACTIVE_COMPILATION_CONDITIONS="DEBUG WATCH_FEASIBILITY"`, using the same derived-data path. The latter opt-in embeds the separately built simulator Watch app. Neither the listener nor the Watch app is embedded by an ordinary Release build. The experiment does not configure provisioning, and this embedding mechanism is simulator-only.

The native-test screen can disable its Watch listener to test the timeout. For repeatable simulator-only runs, launch Watch with `--watch-auto-countdown` and/or `--watch-auto-send`; launch iPhone with `--watch-no-listener` to withhold the JavaScript listener. The countdown requests and message outcomes are logged without message payloads. These options do not exist in release or physical-device execution.

## Simulator evidence (2026-11-18)

Xcode 27.2, paired iPhone 17 Pro simulator (iOS 26.5) and Apple Watch Series 12 simulator (watchOS 27.2): simulator launch arguments invoked the same countdown and send methods as the Watch buttons; direct button interaction was not tested because the Simulator UI was unavailable to computer control. The 60-second timer displayed 00:55 and 00:31 and logged requests at 5, 4, 3, 2, 1 and 0 at one-second intervals. The display dimmed by completion, so the full 00:00 screen was not verified. Native receipt preceded the JavaScript confirmation and Watch's `JS processed` status. With the JS listener withheld, native receipt timed out and Watch reported the negative result. This is simulator evidence only, not proof of physical haptic delivery or locked/background/force-quit behavior.

Unsigned ordinary Debug and Release iPhone simulator builds with production web assets passed; neither binary contained the receiver or plugin symbols, and Release contained no Watch experiment bundle. Focused existing timer, race-logger and native-test suites passed 51 tests. The Watch and opted-in iPhone simulator builds also passed.

### Countdown audio addition

The two original mono 22.05 kHz WAV files are bundled only in the Watch Test Watch target (about 35 KB total). Both are 880 Hz with the same amplitude and fade envelope, with durations of 150 ms and 650 ms. `AVAudioPlayer` instances are prepared at app startup. Audio is requested on the same monotonic-deadline boundary check as each existing haptic. A callback that skips a boundary does not catch up with missed sounds; starting a new countdown invalidates the previous timer, and Cancel clears its deadline. The sound toggle only gates audio, not haptics. `AVAudioSession.Category.ambient` leaves routing and silent behavior to the system. Apple's documentation describes mixing with other audio and silence on screen lock and the iPhone Ring/Silent switch; watchOS silent-mode behavior still requires testing on the SE 2 ([AVAudioSession ambient category](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/ambient)). Background audio is enabled only on the isolated Watch Test target for the active workout experiment.

Audio cue timing is logged separately as `audio request N` only when the local player accepts playback. Such a log is not evidence of audible output. Verify waveform timing and audibility on the physical SE 2, including silent mode, screen-off, lowered wrist, interruptions and route selection. No physical audio result is claimed by simulator builds.

On 2026-11-20, the isolated Watch Test Release app ran on the existing paired iPhone 17 Pro / Apple Watch Series 12 simulators (iOS 26.5 / watchOS 27.2), started with `--watch-auto-countdown`. Logs showed exactly one haptic request and one accepted audio-playback request at each of 5, 4, 3, 2, 1 and 0, with one-second spacing and no extra requests. The packaged WAV durations were 0.150 s and 0.650 s. This verifies countdown boundary/request behavior and bundle contents in simulation only; it does not verify audible output, the toggle's interactive state, physical haptics, wrist-down behavior or audio while the Watch app is suspended.

### Screen sleep and resumption

The owner reports that the latest TestFlight countdown appears to stop while the SE 2 screen sleeps and resumes afterward; the owner recalls the original `d754ba9` candidate behaving differently. Both `d754ba9` and `1041a32` use a `systemUptime` deadline and a repeating timer, with no explicit scene reactivation handling. The latter adds audio session setup, audio preloading and controls, but this comparison does not establish audio as the cause. Timer callbacks and UI updates can stop while the app is suspended; the report does not by itself distinguish stale UI from a clock that excludes device sleep.

The candidate now uses `ContinuousClock`, documented by Apple to advance during system sleep ([ContinuousClock](https://developer.apple.com/documentation/swift/continuousclock)). It stops the foreground timer on scene inactivity and recomputes remaining time immediately on activation without emitting a cue for the resumed update. A callback gap over 300 ms also suppresses its cue, even if the scene transition was not delivered first. This favors avoiding a late start signal over guaranteeing cues under load. A deterministic test advances an injected clock while suppressing callbacks: after 10 seconds the display is 50, remains stale during a simulated 20-second suspension, and updates to 30 on resume. It also checks resume after the deadline, skipped boundaries, cancellation and a late zero. Run it with `mkdir -p /tmp/tackwise-watch-swift-cache && xcrun swiftc -module-cache-path /tmp/tackwise-watch-swift-cache ios/App/WatchFeasibility/CountdownState.swift tests/watch-feasibility/CountdownStateTest.swift -o /tmp/tackwise-watch-countdown-test && /tmp/tackwise-watch-countdown-test`.

The updated candidate built and launched on the paired simulators; a screenshot showed its countdown advancing. The deterministic clock test and 51 focused existing tests passed; ordinary Debug and Release simulator builds passed. The ScrollView is focusable for Digital Crown scrolling, but physical scrolling, sleep and audio behavior are not yet verified.

Physical retest, pending a separately approved internal build: start the 60-second countdown and a reference timer together. Lower the wrist for 20 seconds, wake the Watch, and compare remaining time immediately. Repeat with the wrist lowered until the reference exceeds 60 seconds: the Watch should show 00:00/Complete without a late zero cue. With the screen awake, verify the five short beeps, same-pitch long zero beep and retained haptics; check sound off and cancellation. Scroll to every control using swipe and the Digital Crown. Repeat screen sleep across the final seconds and record whether each cue was actually heard or felt. Accurate resumed time does not ensure wrist-down audio or haptics, and a terminated app has no persisted deadline in this experiment.

### Opt-in sailing workout (physical tests NOT RUN)

The owner authorized a bounded, genuine sailing workout experiment, not a workout created merely to obtain countdown runtime. The Watch Test target has the HealthKit entitlement and the `workout-processing` and `audio` watch background modes; it supplies Health read/write usage descriptions. Apple requires the workout mode and specifies audio mode when using audio or haptics during an active workout ([Running workout sessions](https://developer.apple.com/documentation/healthkit/running-workout-sessions)). No production target or signing identity is changed. App Review acceptance is not established: before distribution the owner must review whether the test app provides a genuine health/fitness service, its descriptions and reviewer instructions, and obtain the necessary Apple Developer HealthKit capability and matching provisioning.

The sailor opens Sailing workout and explicitly selects Allow & start for a real sailing activity. HealthKit then requests workout write and heart-rate read permission. The screen displays elapsed duration and the most recent heart rate when available; read access can be denied without HealthKit revealing that denial, in which case heart rate may remain unavailable. Workout status and End & discard remain on the separate workout screen. A small toolbar route reaches that screen without putting workout actions or status on the primary countdown face. The session is not ended at the countdown gun. The app attempts to recover a system-recoverable active workout after a crash; if recovery fails it does not permit a new session and directs the user to check the Watch workout. Test this recovery and the system end control on a physical device.

Keeping the session active after the gun is an explicit instruction for this isolated experiment. The approved v1.3 product proposal instead calls for its background session to end at the gun; this experiment does not change that product decision.

The app ends the session and discards the workout builder; it does not save an HKWorkout or write its own health, location, heart-rate log, account or cloud records. Discarding the workout does not promise that all samples generated by watchOS during the active session are deleted: HealthKit may persist heart-rate or other workout-related samples. Users can inspect and manage Health data through Apple's Health controls. The configuration uses `.sailing` with an unknown location type and requests no location permission or app GPS collection; Apple controls workout sensor processing, so no claim is made that the system collects no location. An active workout uses sensors and background execution and can increase battery consumption.

Health information is sensitive personal data. Internal testers must explicitly opt in with clear information about purposes, collection, retention and Health permissions. The app does not log health values or send them to the iPhone or network; Apple manages any system Health synchronization. Before a signed test distribution, review lawful basis and applicable special-category conditions, data inventory, notice, retention/deletion and any App Store privacy disclosure, plus security and CRA risk evidence. These notes are engineering evidence, not legal or App Review approval. Distribution and provisioning remain separate owner approval gates.

Validation on 2026-11-20: unsigned candidate Release simulator build and native Watch launch passed. The Watch bundle contains both usage descriptions and the two intended background modes. Ordinary iPhone Debug and Release simulator builds passed and contain no Watch experiment or workout symbols. The deterministic countdown test and 51 focused existing timer, native-test and race-logger tests passed. Permission prompts, HealthKit session lifecycle, heart-rate readings, recovery and discarding have not been exercised on a physical Watch; a simulator launch does not establish those behaviors.

### Countdown face presentation

The primary face uses large, dominant remaining-time digits and keeps Start, Cancel, sound and test-message controls in a focusable scroll view. The workout's Start and End & discard actions remain on a separate screen reached through the small toolbar navigation control; no workout status label or lifecycle button is shown in the countdown content. A red heart and bpm appear only while a positive, finite sample from the active workout is no more than 30 seconds old. Otherwise the main face shows no heart-rate value. The 2026-11-20 Watch Series 12 simulator capture showed the large countdown and toolbar control, with lower controls continuing below the visible area. Digital Crown interaction and fit/scroll behavior on the physical SE 2 still require owner testing.

# Watch feasibility experiment

Feasibility spike related to [PR #80](https://github.com/anflyg/SailRaceApp/pull/80). This is not a Watch product or a race-start path. The watch derives remaining time from a continuous monotonic deadline and requests a click at 5–1 and a success haptic at zero only when its timer callback runs promptly. The isolated Watch Test candidate also preloads a 150 ms beep at 5–1 and a 650 ms beep at zero, using the same pitch and timbre. Haptics remain enabled independently of the sound toggle. Missed cues are not replayed; cancelling stops the countdown and later cues. A user-started sailing workout requests workout background runtime.

The iPhone activates the WatchConnectivity receiver only in a Debug simulator build explicitly compiled with `WATCH_FEASIBILITY`. A validated, random test ID is emitted to the Capacitor `watchTest` listener in the existing guarded native-test web app; the receiver replies `processed: true` only after JavaScript calls `confirm` for that pending ID. A missing listener, invalid message, duplicate pending ID or five-second timeout yields no successful acknowledgement. Native receipt is logged without payloads; this does not record a race. No queued command is used. The native-test asset guard blocks release/archive/distribution.

## Simulator procedure

From this worktree run `npm ci`, `npm run build`, `npx --no-install cap sync ios`, then `npm run cap:copy:native-test`. Build the `WatchFeasibility` scheme for watchOS Simulator Debug unsigned first. Build the `App` scheme for iOS Simulator Debug with `CODE_SIGNING_ALLOWED=NO SKIP_INSTALL=YES` and environment variables `TACKWISE_NATIVE_TEST_BUILD=1 TACKWISE_WATCH_FEASIBILITY=1`, plus build setting `SWIFT_ACTIVE_COMPILATION_CONDITIONS="DEBUG WATCH_FEASIBILITY"`, using the same derived-data path. The latter opt-in embeds the separately built simulator Watch app. Neither the listener nor the Watch app is embedded by an ordinary Release build. The experiment does not configure provisioning, and this embedding mechanism is simulator-only.

The native-test screen can disable its Watch listener to test the timeout. For repeatable simulator-only runs, launch Watch with `--watch-auto-countdown` and/or `--watch-auto-send`; launch iPhone with `--watch-no-listener` to withhold the JavaScript listener. The countdown requests and message outcomes are logged without message payloads. These options do not exist in release or physical-device execution.

### Physical audio and haptic findings

Owner-reported physical feedback on Apple Watch SE 2 / watchOS 26.6: countdown audio and haptics were delivered with the wrist down during an active Sailing Workout. At 0:00, two audible sounds overlap. The current code requests the 650 ms custom `CountdownZero.wav` and `.success` at the same boundary. The owner suspects the additional sound comes from the system haptic. This is consistent with Apple's HIG, which says watchOS combines Taptic Engine patterns with an audible tone ([Playing haptics](https://developer.apple.com/design/human-interface-guidelines/playing-haptics)); the exact sound component has not been independently isolated.

The owner subsequently reports that the opt-in automatic Sailing Workout start and wrist-down countdown audio worked on the SE 2. This is owner-reported evidence for those specific paths; it does not establish the synchronization prototype, failure paths, haptic strength, background iPhone delivery or other device cases.

The supported `WKInterfaceDevice.play(_:)` API selects a system haptic pattern and provides no option to suppress its associated tone ([WatchKit haptic API](https://developer.apple.com/documentation/watchkit/wkinterfacedevice/play%28_%3A%29)). Core Haptics is not listed for watchOS in Apple's framework documentation ([Core Haptics](https://developer.apple.com/documentation/corehaptics)). Accordingly the app retains the noticeable `.success` zero haptic and the custom 880 Hz/650 ms beep; there is no supported silent replacement established by this experiment. A regression test locks the 5–1 `.click` + short sound mapping and zero `.success` + long sound mapping so a weaker haptic is not introduced implicitly.

The owner accepts the paired system tone over the zero beep. Other alternatives would require a product decision and physical retest: replace the custom zero beep with the `.success` pattern's system tone (loses the required custom 650 ms beep); use a weaker `.click` for zero (may compromise sailing feedback); or sequence the system haptic and custom beep (delays one zero cue and may still create a second audible tone). Do not claim a silent, strong system haptic is available.

On the paired iPhone 15 / Watch SE 2, retest the short tone at 5–1 and the longer zero tone with sound enabled/disabled, foreground/wrist-down during the active workout, and the system silent settings. Record both haptic feel and audible output separately. The candidate sets the ambient audio-session category, follows system routing, and does not force an output route. Check the Watch Silent Mode and available audio routes; the iPhone ambient-session documentation does not establish Watch Silent Mode behavior. No change to workout, countdown timing or background capabilities is implied by these findings. H1–H3 involving HealthKit remain NOT RUN and require separate approval.

### Countdown audio addition

The two original mono 22.05 kHz WAV files are bundled only in the Watch Test Watch target (about 35 KB total). Both are 880 Hz with the same amplitude and fade envelope, with durations of 150 ms and 650 ms. `AVAudioPlayer` instances are prepared at app startup. Audio is requested on the same monotonic-deadline boundary check as each existing haptic. A callback that skips a boundary does not catch up with missed sounds; starting a new countdown invalidates the previous timer, and Cancel clears its deadline. The sound toggle only gates audio, not haptics. `AVAudioSession.Category.ambient` leaves routing and silent behavior to the system. Apple's documentation describes mixing with other audio and silence on screen lock and the iPhone Ring/Silent switch; watchOS silent-mode behavior still requires testing on the SE 2 ([AVAudioSession ambient category](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/ambient)). Background audio is enabled only on the isolated Watch Test target for the active workout experiment.

Audio cue timing is logged separately as `audio request N` only when the local player accepts playback. Such a log is not evidence of audible output. Verify waveform timing and audibility on the physical SE 2, including silent mode, screen-off, lowered wrist, interruptions and route selection. No physical audio result is claimed by simulator builds.

On 2026-11-20, the isolated Watch Test Release app ran on the existing paired iPhone 17 Pro / Apple Watch Series 12 simulators (iOS 26.5 / watchOS 27.2), started with `--watch-auto-countdown`. Logs showed exactly one haptic request and one accepted audio-playback request at each of 5, 4, 3, 2, 1 and 0, with one-second spacing and no extra requests. The packaged WAV durations were 0.150 s and 0.650 s. ### Screen sleep and resumption

The owner reports that the latest TestFlight countdown appears to stop while the SE 2 screen sleeps and resumes afterward; the owner recalls the original `d754ba9` candidate behaving differently. Both `d754ba9` and `1041a32` use a `systemUptime` deadline and a repeating timer, with no explicit scene reactivation handling. The latter adds audio session setup, audio preloading and controls, but this comparison does not establish audio as the cause. Timer callbacks and UI updates can stop while the app is suspended; the report does not by itself distinguish stale UI from a clock that excludes device sleep.

The candidate now uses `ContinuousClock`, documented by Apple to advance during system sleep ([ContinuousClock](https://developer.apple.com/documentation/swift/continuousclock)). It stops the foreground timer on scene inactivity and recomputes remaining time immediately on activation without emitting a cue for the resumed update. A callback gap over 300 ms also suppresses its cue, even if the scene transition was not delivered first. This favors avoiding a late start signal over guaranteeing cues under load. A deterministic test advances an injected clock while suppressing callbacks: after 10 seconds the display is 50, remains stale during a simulated 20-second suspension, and updates to 30 on resume. It also checks resume after the deadline, skipped boundaries, cancellation and a late zero. Run it with `mkdir -p /tmp/tackwise-watch-swift-cache && xcrun swiftc -module-cache-path /tmp/tackwise-watch-swift-cache ios/App/WatchFeasibility/CountdownState.swift tests/watch-feasibility/CountdownStateTest.swift -o /tmp/tackwise-watch-countdown-test && /tmp/tackwise-watch-countdown-test`.

The updated candidate built and launched on the paired simulators; a screenshot showed its countdown advancing. The deterministic clock test and 51 focused existing tests passed; ordinary Debug and Release simulator builds passed. The ScrollView is focusable for Digital Crown scrolling, but physical scrolling, sleep and audio behavior are not yet verified.

#### Reliability investigation, 2026-11-21–22

The baseline `31d23ed` reproduced the owner's observation through real simulator UI: pressing iPhone START advanced the phone while Watch stayed at 5:00 and SOLO. Code inspection identified several causes:

- Every transient failure permanently latched SOLO and ignored subsequent phone notifications. Automatic recovery now retries transient failures; only an independently edited/conflicting timeline requires explicit Rejoin.
- The initial Crown/on-appearance assignment could cancel an in-flight exchange even when the preset did not change. No-op assignments now return before changing sync state.
- One-second reply deadlines and a six-second freshness check raced multi-exchange handshakes. Observed WatchConnectivity round trips were approximately 2–3.3 seconds, including one instrumented exchange with zero milliseconds of phone main-queue processing. Requests/application ACKs now have five-second deadlines; freshness expires after fifteen seconds and does not race an in-flight exchange. Confirmation remains an expiring diagnostic, not a delivery guarantee.
- Watch START required already-SHARED state, losing the user's intent during startup. A bounded pending intent now obtains a fresh phone snapshot/lease and reconciles a lost response using the phone's last accepted command ID. An accepted START gets a new timeline UUID; PAUSE retains it. Duplicate/stale rejections are identified separately from preset conflict. Commands expire after ten seconds; they must not start a new phone countdown later after an outage. Expiry preserves the Watch timer and requires deliberate reconciliation. The existing two-second lease remains unchanged.
- A Watch PAUSE could be blocked before delivery by uncertainty in a running snapshot. Command preflight now checks provenance/revision/lease independently of running-time calibration. The accepted frozen PAUSE state does not need transit estimation. An unknown phone timeline is still protected from Watch PAUSE.
- Routine confirmations used to re-anchor an unchanged local countdown, suppressing imminent cues. Same-timeline/revision confirmations now retain the existing anchor; only changed authoritative state replaces it, with rollback on failed application ACK.

Compatible idle state automatically establishes SHARED. A prepared Watch opened after phone START attempts to join automatically; a known timeline follows authoritative phone START/PAUSE updates, including notifications missed during transient failure. Independent Watch resume, skip and reset remain local and require explicit Rejoin before adopting phone state. The phone is never overwritten with a Watch deadline. Preset conflict handling is still deliberately incomplete: mismatched START fails closed; full offline preset propagation remains a future product task.

Clock correlation uses bounded interval estimates of **phone minus Watch clock offset**, derived from local send/receive and phone receive/sample times; device-local monotonic epochs are never equated. Up to sixteen exchanges within thirty seconds can narrow the interval. The experimental drift allowance is 1000 ppm plus 1 ms timestamp precision and needs device validation. Running-time adoption still requires uncertainty at most 250 ms and a sample no older than ten seconds. Contradictory calibration resets the interval. Frozen/idle states do not require accurate transit estimation. Polls occur every five seconds when calibrated, or every two seconds while retrying/calibrating; there is no per-second synchronization traffic. Excessive uncertainty, lost replies or discrepancies preserve local timing and do not claim SHARED. These are prototype parameters, not approved protocol guarantees or evidence of synchronized gun safety.

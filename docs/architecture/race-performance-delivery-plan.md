# Race performance — lean implementation plan

**Owner-directed execution order: 2026-11-26.** This is the **current delivery plan** for D1–D11. It replaces the sequencing, not the technical acceptance criteria, of the more detailed [C0–C19 task reference](race-performance-codex-plan.md). The [product decisions](../product/race-performance-change-decisions.md), [technical design](race-performance-technical-design.md), [C1 lifecycle proposal](decisions/adr-010-vmg-wind-reference-lifecycle.md), [C3 data model](race-performance-g3-data-model.md), and repository `AGENTS.md` remain the inputs. No further generic design inventory is requested.

## What is already done, and what is not

- **Approved product direction:** D1–D11, including manually controlled tack angle, Wvmg frozen between accepted calibrations, a first valid post-gun W0 when none existed, 0–15 m bow offset, corrected A/B capture, favored-end bias, and calibrated R/S presentation.
- **Design/research completed as proposals:** C1 lifecycle, C3 minimized history/raw-v2 candidate, and C13 synthetic maneuver feasibility ([API draft PR #59](https://github.com/anflyg/tackwise-api/pull/59)). ADR-010/011/012 remain **PROPOSED**; synthetic acceptance fixtures are not executed native evidence.
- **Not implemented or approved for release:** the new live VMG path, iPhone start/R/S changes, persistent history/checkpoints, raw-v2, backend/web analysis and higher-frequency logging.

Each stage may be split into small sequential PRs with a single owning worktree each. Stage 1 and Stage 2 can start independently **in the same repository only if they do not share an active worktree or competing changes to the same files**; otherwise run sequentially. Stage 3 is **deferred**, not discarded; C3 remains its working design, not an instruction to implement every candidate field. Stage 4 is not part of the initial iPhone delivery.

## Verification and release

- Relevant unit/integration, regression, old-data compatibility and boundary tests for each change. For native/attitude/lifecycle work, real Xcode simulator **Build and Run in the exact implementation worktree**, and physical-device/on-water tests for motion/GPS reliability before a release claim.
- Keep existing owner-only/private data and offline behavior; no new collection, migration, merge, deployment, production flag change, historical rewrite or data deletion without explicit authorization. Code merged, tested or shown in an internal preview is not by itself production approval.
- Report only changed files, tests, actual blockers and the next safe action. Do not repeat C0/C1/C3 general investigation or create another full-plan PR. Record any **new** security/privacy/architecture decision in the relevant ADR only when the implementation truly needs it.

## Can one Codex prompt do everything?

**Not recommended across all repositories.** A single long session spanning iPhone, shared contracts, backend and web would mix distinct approval gates, invite shared-file collisions, produce oversized reviews and consume credits on retries.

**Practical compromise:** one prompt for a **single bounded iPhone stage** (or one focused local-only work package), sequential commits and tests, one draft implementation PR, no merge. Use a second prompt for VMG if start/attitude work touches the same files. **Do not ask that prompt to invent raw-v2, modify production API, or silently close G1–G4.** Reuse this plan as the context for later short prompts instead of repeating its content.

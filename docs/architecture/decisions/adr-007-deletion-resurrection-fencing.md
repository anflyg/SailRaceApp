# ADR-007: Deletion resurrection fencing

**Status:** PROPOSED — NOT ACCEPTED.

**Date:** 2026-10-17

## Problem, scope and proof obligation

[ADR-006](adr-006-cross-store-race-and-account-deletion.md) requires race and account deletion to exclude delayed PostgreSQL work and external R2 writes, including a PUT started before deletion but committed afterward. An expired SQL lease, a database preflight, a `HEAD` showing absence, and a grace interval do not prove that an external PUT has stopped. A post-delete PUT to the same key can recreate personal telemetry after deletion was reported complete.

This proposal covers the authenticated upload path, abandoned-upload cleanup and operator recovery, analysis dispatch/consumer/result publication, D2–D4 deletion state, direct privileged database writes, and account/Auth removal. It designs no public endpoint and makes no runtime, migration or resource change. The proposed protocol is **not** evidence that D5 is implemented or that production deletion is safe. It must be accepted, implemented, provider-validated and drilled before D6 or deletion enablement.

The adversary includes a delayed or crashed Worker, a duplicated queue delivery, a privileged writer bypassing an application service, a provider timeout with unknown outcome, and a stale write that commits after a database lease expires. A compromised R2 credential or an independent privileged R2 writer outside this protocol is outside its guarantee and must be prevented by credential inventory, least privilege and incident containment; it cannot be assumed away.

## Existing boundaries reviewed

The `tackwise-api` main implementation through migration **00018** has these relevant properties:

| Boundary | Existing behavior and gap |
| --- | --- |
| Upload | `RaceUploadContentService` validates bytes, obtains `begin_race_upload_content_write`, then `R2RaceContentAdapter` does GET-before-**unconditional** PUT to the ADR-003 raw key. `finish_race_upload_content_write` clears a matching token. An expired token does not stop an already submitted PUT. Prepare/finalize use a reservation and accepted-race RPC; no deletion gate is checked. |
| Cleanup/recovery | Migrations 00008–00012 coordinate reservation, race insert, cleanup and operator recovery with row locks/leases. Expired uncertain content writes preserve the reservation and reference; the operator recovery path can inspect/delete an orphan. Migration 00009/00012 guards race INSERT against claimed cleanup/recovery and orphan tombstones. These mechanisms do not fence R2 itself. |
| Analysis | Migrations 00005–00010 provide unique run/version targeting, dispatch and processing leases, finite retries and reconciliation. The maintenance Worker sends a two-field queue envelope; the route-less consumer claims processing. It currently refuses successful completion because result persistence is not implemented. ADR-005 fixes the future result key and immutable bytes. No result-write fence exists. |
| Deletion | Migrations 00013–00017 add server-only jobs, object inventory/claim/outcome RPCs and account enrollment/progress. `processRaceDeletionObjects` requires the unimplemented `DeletionWriteFence` and otherwise fails before an object attempt. Its pre-DELETE checks are not an atomic R2 fence. Migration 00018 adds read-only race/account preflight and always reports D5 fencing as `not_proven`. No relational deletion or completion transition exists. |
| Account/Auth | Deletion requests create durable jobs, but current upload/analysis paths do not consult them. `profiles` is Auth-FK-backed; removing Auth or allowing cascades too early could erase ownership evidence. |

All versions of these paths, including old deployed Worker versions and privileged SQL/R2 access, must be inventoried during rollout. A migration alone cannot retrofit an already submitted unconditional PUT.

## Alternatives evaluated

| Approach | Benefit | Why it is insufficient alone |
| --- | --- | --- |
| A. Database-only deletion barrier, trigger, row lock or lease | Serializes PostgreSQL commits and rejects new SQL work. | An R2 PUT already sent can commit after the lock is released or the lease expires. |
| B. Durable writer generation/epoch | Rejects stale SQL completion and permits a closed gate to survive Worker restarts. | R2 does not consult PostgreSQL or a separately stored epoch when committing a PUT. |
| C. Immutable, generation-scoped R2 key | Prevents a stale writer from overwriting a *new generation's* object and makes stale keys identifiable. | A stale PUT can still create personal data at its old key after that key was deleted. Key rotation is not deletion or proof of absence. It also changes ADR-003/005 identities. |
| D. Provider conditional PUT at the **same** key | An atomic precondition can make every payload PUT depend on an earlier object state that deletion irreversibly changes. | Requires an initial guard object, protocol changes to all writers, a proven provider contract, and handling of an uncertain guard creation. Conditional PUT alone does not cover legacy unconditional writers. |
| E. Explicit writer drain, repeated HEAD/list or timing | Useful diagnostic/reconciliation evidence. | A worker crash, timeout or long in-flight request makes absence and elapsed time unable to prove future non-commit. A Durable Object mutex has the same crash-to-provider gap unless provider commit is fenced. |

Cloudflare documents [conditional `put` in the Workers R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/): a failed condition returns `null`. Its [S3-compatible API documentation](https://developers.cloudflare.com/r2/api/s3/api/) explicitly says `PutObject` `If-Match`/`If-None-Match` conditions are evaluated **atomically at object commit**. [R2 consistency documentation](https://developers.cloudflare.com/r2/reference/consistency/) says writes, deletes and listings are strongly consistent at the bucket API, but the last completed PUT/DELETE to one key wins; cache-backed public domains have different behavior. The Workers binding documentation does not by itself establish every S3 conditional-commit detail. The reviewed implementation must either obtain that guarantee for binding `onlyIf` or use the documented S3 conditional `PutObject` surface with narrowly scoped server-only credentials. It must handle `null`/`412` as a failed precondition, not success. No current Cloudflare feature is assumed to atomically compare a *different* guard key or to condition an R2 DELETE on PostgreSQL state.

## Proposed two-layer protocol

### 1. Durable SQL admission gates

Introduce a server-only, FK-independent account gate and race-identity gate, provisioned before any covered work. A **missing** gate is closed, never implicitly active. The account gate moves monotonically from active to closing when account deletion is requested; the race gate does the same on race deletion or terminal orphan recovery. Preserve an irreversible generation/revocation record for as long as it is needed to reject stale work; a new lease generation is not permission to reopen a closed identity. Reopening or UUID reuse is not part of this proposal.

Every trusted RPC and relevant `INSERT`/`UPDATE` trigger must validate both gates under the same database transaction as its lifecycle change. All admission operations acquire **account gate → race gate → existing reservation/race/run/job locks** in a reviewed global order. Database writes that cannot acquire the gates in order fail/retry without side effects; direct privileged DML is not exempt. A transaction admitted before deletion may commit before the deletion request obtains the gate locks; afterward no new covered commit may succeed. Deletion does not interpret this serialization as proof that its earlier external PUT is finished.

Account deletion closes the account gate first, then enumerates races and durable R2 references while ownership is still available. Race deletion closes the race gate before D3 object inventory/claims. Existing request RPCs, cleanup/recovery, dispatch/processing and any direct-INSERT triggers need forward-only revisions; current lock orders and row-level UPDATE triggers require deadlock analysis and controlled `NOWAIT`/retry where an earlier row lock cannot be avoided. SQL roles with direct table-write authority must be reduced or covered by the same database guard. Missing/legacy gates and contradictory ownership fail closed for reviewed backfill, never silently become active.

### 2. One-shot, same-key R2 write admission and sealing

For **each exact raw or derived-result key**, create an opaque, random, non-payload **guard object at that same key** using conditional `If-None-Match: *`. Durably register the key, guard identity/ETag, write generation and guard-creation outcome before authorizing any payload PUT. Only one guard-create attempt per key may be in flight; an ambiguous attempt is durable uncertainty, not authorization for a second attempt. The guard and its key are private, server-only recovery state. The current raw and ADR-005 result key formats remain unchanged; this is a proposed change to what may temporarily occupy them.

Every payload PUT is **one-shot and conditional `If-Match: <registered guard ETag>`** at that same key. A retry reuses that exact condition and immutable bytes, never GETs a new ETag to renew authority and never uses unconditional PUT or payload `If-None-Match`. An existing payload is verified for identity and reused, never overwritten. Guard creation must have definitively completed before any payload PUT is dispatched. SQL completion must still check current race/account gates and lease generation; a failed SQL completion after a successful R2 PUT leaves a registered, reconcilable object. A failed R2 condition or ambiguous provider result is a safe error, never a blind retry with a new condition.

Before D3b or orphan recovery can call R2 DELETE or accept `absent`, the trusted object processor **seals the exact key**: it atomically replaces the observed guard or payload with a distinct, private, non-payload seal object using conditional `If-Match` on the observed ETag. If the conditional PUT loses to a payload writer, reread and retry against the resulting state under the still-closed SQL gates; do not infer absence from a stale read. Verify and durably record the seal identity/outcome. Only then delete the seal object at that key and confirm exact-key absence. Unknown seal, DELETE or confirmation outcomes keep the object/job unresolved and its reference durable. The seal operation must never overwrite an accepted object's data outside an authorized deletion/recovery workflow.

**Why a late payload PUT fails:** every payload request carries the original guard ETag `G`. If it commits before the seal, the seal's first conditional write fails, then retries against the payload's new ETag. If the seal commits first, the old request's `If-Match: G` fails atomically. Once the seal has replaced `G`, deleting the seal leaves the key absent, which also cannot satisfy `If-Match: G`. A request that timed out locally but later reaches R2 has the same condition. A later payload request must not be allowed to acquire a new guard/generation for the closed race. Distinct random guard/seal bodies must have different checked ETags; ETag and provider behavior must be validated, not treated as an application secret or a substitute for SHA-256 of payload bytes.

This proof requires **all** payload writers, including retries and future result publishers, to use that one-shot condition and the same private bucket identity. The current unconditional raw PUT and any legacy in-flight request violate the premise. Guard creation is itself a conditional external write: if it remains in flight or its outcome is ambiguous during deletion, a late guard may reappear after the seal is removed. It cannot create telemetry without a later authorized payload PUT, but it can leave pseudonymous key/state. Do not mark deletion complete or remove its recovery reference until guard creation is conclusively settled by provider evidence and reconciled; a HEAD/grace interval alone is not conclusive. If such evidence is unavailable, keep the case unresolved and escalate. There is no claim that the proposed protocol guarantees completion for arbitrary legacy or ambiguous guard writes.

The proposed guard temporarily occupying the deterministic result key differs from ADR-005's literal **create-only-if-absent** result-object rule; its deletion seal also changes a stored object's contents before removing it. Acceptance requires an explicit ADR-005 amendment defining private guard/seal states without weakening immutable *payload* bytes or the fixed result key. ADR-003 raw-key/idempotency language needs the same reviewed clarification. This proposal does **not** silently amend either accepted ADR.

## Required enforcement by path

“Gate” below means both owner/account and race gate checked transactionally; a valid lease alone is never sufficient. An external mutation also requires the same-key conditional protocol above. Each rejection must be sanitized and leave durable recovery evidence.

| Path | Authoritative state and current coordination | External effect / failure and retry | Required D5 fence and resurrection race |
| --- | --- | --- | --- |
| Upload prepare and reservation INSERT | Auth-derived owner, `profiles`, `race_uploads`; reservation uniqueness/idempotency, no deletion check. | No R2 yet; duplicate/retry can recreate a reservation. | Lock account/race gates before insert; reject closing/missing gate, including privileged direct INSERT and a retry after reservation removal. |
| Content-write begin | Reservation row/token with one-hour expiry in 00008. | Authorizes later R2 PUT; an expired token can outlive that PUT. | Gate check under reservation lock; persist the one-shot object guard/attempt identity before external work. No second payload authority from lease expiry. |
| Raw R2 PUT and finish | Current Worker GET-then-unconditional-PUT; finish matches token. | PUT may commit after timeout, crash, deletion or failed finish. | Conditional payload PUT against registered `G`; seal wins/retries at R2. Finish checks gate/generation; stale finish cannot reopen or clear uncertainty. |
| Finalize / accepted race INSERT | `accept_race_upload`, reservation/entitlement locks; 00009/00012 race-INSERT trigger coordinates cleanup/tombstones. | R2 GET/verification precedes SQL acceptance; ambiguous SQL response retries. | Gate check in acceptance transaction and INSERT trigger, including matching accepted-race idempotent branch; no acceptance after close. Preserve exactly-once Free accounting. |
| Abandoned cleanup | Reservation claim/lease and accepted-race recheck; 00011 preserves expired uncertain writes. | R2 DELETE/finish may be uncertain; stale PUT may recreate orphan. | Account/race gate and existing reservation serialization; seal before orphan DELETE/absence. `cleanup_content_write_uncertain` remains operator-only until proved, never cleared by elapsed time. Accepted match remains reservation-only. |
| Operator orphan recovery | Recovery lease/audit and reservation/race locks in 00012/00014; orphan outcomes leave tombstones. | Exact-key inspection/deletion may be uncertain. | Gate closes for terminal orphan recovery, seal before object absence/deletion; create retained, owner-linked post-reservation integrity state. `accepted_match` preserves accepted object. |
| Analysis run creation and reconciliation | Unique `(race_id, analysis_version)`, required version and accepted race; finite work state. | Creates new SQL work; missed sends are retried. | Gate check in ensure/reconcile RPCs and analysis-run INSERT/UPDATE triggers; no new or reactivated run after close. |
| Dispatch and Queue send | Dispatch claim lease/attempt; Queue send has at-least-once/unknown outcome. | A message may arrive after deletion. | Gate check before claim and before send; a prior send is harmless only if consumer claim rechecks closed gate. Do not rely on queue purge. |
| Queue consumer claim / processing | Processing lease and raw identity from DB, minimal envelope; current consumer has no result publisher. | Old message/processor may continue after lease loss or gate close. | Gate check in claim and finish plus run/race UPDATE triggers; no raw read or new processing after close. An already started external result PUT still needs the R2 seal protocol. |
| Analysis result PUT, completion and retry | ADR-005 deterministic key/bytes; result writer/completion not yet implemented. | PUT can complete after lease expiry; DB completion may fail. | Register and condition result PUT on its own `G`; seal result key during deletion. Completion/retry checks gate and current lease, never publishes after close; historical runs included. |
| D3 object deletion and D4 relational deletion | Durable jobs/registry, lease generations, 00018 read-only preflight; `DeletionWriteFence` currently absent. | R2 DELETE and DB transitions may be ambiguous. | Closed gates plus per-key seal/confirmed absence. Revalidate under final SQL locks immediately before removing `analysis_runs`, `races`, reservation or references; preflight result is not a capability. |
| Account completion, Auth removal and cascades | Account job/progress, profile FK to Auth. | Auth deletion can cascade away ownership evidence; old client/Worker may retry. | Keep gates, ownership and exact object references until races, objects, audits and required retention are resolved; Auth is the last external identity operation. Missing account gate rejects stale work. |

All relevant `races`, `race_uploads`, `analysis_runs`, result metadata, deletion-job and recovery-audit INSERT/UPDATE paths must be inventoried and guarded, not just the named RPCs. Deletion/recovery state transitions are allowed only for current server claims; generic service-role table writes and old Worker deployments must not bypass the invariant. Do not put client-supplied owner, key or gate generation in authority decisions.

## D3/D4 integration and completion boundary

`DeletionWriteFence.assertRaceFenced` may verify a closed SQL gate, owner, generation, source inventory and absence of unauthorized writers; it cannot by itself certify R2. `assertObjectFenced` must **establish and durably verify** the exact-key R2 seal before the first `exists`/`DELETE` decision and be idempotent on the second call. The current `void` interface and D3b `exists → DELETE` control flow do not distinguish guard, seal and payload states or persist seal outcomes; a reviewed D3b adapter/interface change is required. No `writeFence` implementation may merely query the database or check lease expiry. Claims of `deleted` or `absent` require the exact bucket/key, original guard identity, seal evidence, resolved provider outcome and current SQL gate; previously uncertain objects are reconciled at that exact identity without blind DELETE or reissued payload PUT. An empty object registry never proves absence.

D4b2 must lock account/race gates in the agreed order, re-read every dependency and object outcome within its guarded transaction, and retain the registry and ownership references across uncertain R2/SQL results. It must not trust a prior 00018 preflight response or advance `deleting_relational`/`completed` on unresolved provider state, missing inventory, uncertain guard/seal, legacy writer, tombstone ownership or D5 status. Delete/close analysis runs, race and reservation only after object outcomes are resolved; Auth/profile/entitlement/audit ordering follows ADR-006 and the retention policy. Fencing state must survive worker restarts, attempt exhaustion and partially removed source rows.

## Tombstones, UUID reuse and retention

Migration 00012's orphan tombstone protects a race after its reservation disappears. A proposed removal transaction must prove verified ownership (NULL-owner legacy records require separately reviewed evidence), no accepted/reserved/source work or unresolved R2 identity, closed account/race gate, all old guard/payload/seal attempts resolved or fenced at R2, and a durable replacement admission rule that rejects delayed privileged INSERTs **after** the tombstone row is gone. All direct race inserts must consult that rule, and a delayed transaction must serialize against the removal transaction. `accepted_match` is not an orphan tombstone and never authorizes object deletion.

The proposed race gate can replace the orphan tombstone's *insert-blocking role* while the account exists, but it remains pseudonymous integrity state. Deleting both gate and tombstone while the current client-generated UUID can be re-prepared would silently permit UUID reuse. A permanent UUID denylist would also retain pseudonymous data indefinitely and is **not** approved by ADR-006. No complete, retention-bounded safe-removal rule follows from the current design. A concrete candidate for review is server-issued canonical cloud race IDs with non-reissuable issuance state, separate from the offline local ID, plus fail-closed admission when an account gate is absent. That changes ADR-003's client-generated cloud UUID and needs an explicit decision; merely using random server UUIDs without a non-reissuance rule is not a proof. If completion requires retaining pseudonymous closed gates after other data is removed, ADR-006's completion/retention rule must also be explicitly amended with a justified scope and period. Before D5/D6 acceptance, decide these policies and how Auth/provisioning prevents old account UUID reactivation. Until then keep affected deletion/recovery unresolved and the necessary protection in place; do not claim completed deletion or a GDPR retention exception by implication. Provider backups and exact retention periods also need privacy review.

## Deterministic acceptance matrix

Use two PostgreSQL sessions/barriers and a controllable R2 conditional-commit model, then reproduce the critical orderings in an isolated **non-production** R2 bucket/Worker. No sleeps, production keys, personal telemetry or real accounts. Assert durable state, R2 content/absence, rejected stale operations and sanitized aggregate logs after each forced pause/crash. A mock alone is not provider-semantic proof.

| Forced ordering | Required safe outcome |
| --- | --- |
| Payload PUT starts on guard `G`; deletion closes gate; PUT commits first. | Seal CAS initially loses/retries against payload, then succeeds; exact key is removed before completion. |
| Deletion seals `G` first; delayed PUT tries to commit afterward. | Atomic `If-Match: G` fails; no payload reappears after seal DELETE. |
| PUT succeeds; SQL finish/acceptance fails or response is lost. | Closed gate rejects stale SQL completion; registered object is sealed/deleted or remains unresolved with reference, never forgotten. |
| DELETE succeeds while a conditional PUT is in flight. | Already verified seal means old guard condition cannot match absent key; later PUT fails. A legacy unconditional PUT instead blocks completion until separately proven quiescent. |
| Content/processing lease expires while external PUT continues. | Expiry grants no deletion/overwrite authority; seal resolves the race or uncertainty remains durable. |
| Stale/duplicate Queue message arrives after race/account close. | ACK/no-op or bounded transport handling without processing attempt, raw read or result write; DB claim rejects. |
| Result publication races with close; historical run exists. | Its conditional PUT either precedes and is sealed/deleted, or loses to seal; no run/result completion after close; all versions inventoried. |
| Cleanup claim races with finalize/direct race INSERT. | Existing reservation serialization yields accepted-preserving reservation-only outcome or rejected insert; no accepted object DELETE. |
| Account close races with prepare/content/finalize on a new race. | Account-gate lock orders commits; after close no new reservation, race, run or R2 payload admission. |
| Worker crashes after guard, payload, seal or DELETE provider mutation. | Reconcile durable exact-key state; never promote uncertainty to completed by elapsed time or a single negative HEAD. |
| Tombstone removal races with delayed privileged INSERT. | Replacement closed gate/issuance rule rejects insert after removal; if that rule is unproven, removal/completion is refused. |
| Provider timeout/ambiguous conditional PUT or DELETE. | Preserve object identity, guard/seal attempt and bounded error state; reconcile provider outcome, then retry only a safe conditional transition. |
| Worker restarts or automatic retries exhaust. | Gates remain closed, generations monotonic, no fresh payload authority; unresolved state is operator-visible and deletion not complete. |

## Implementation sequence and release gates

1. **D5b — SQL admission and rollout inventory:** reviewed forward migration for account/race gates, ownership and generation, trigger/RPC coverage, lock order and legacy backfill. Keep all deletion and result publication disabled. Test direct privileged DML, account/race request races, stale generations and cascades.
2. **D5c — Conditional R2 write protocol:** choose and validate the provider API; add unique guard registration, conditional raw/result writers, private seal/reconciliation state and credential controls. Explicitly amend ADR-003/005 as approved. Prove real R2 conditional commit orderings with isolated synthetic objects; audit old unconditional writers and ambiguous guard attempts.
3. **D5d — D3b/D4b2 integration:** implement `DeletionWriteFence` as actual per-key sealing and evidence, adapt object processor/preflight/relational deletion to guard and seal states, and preserve references through uncertainty. No production deletion activation merely because these PRs merge.
4. **D5e — Tombstone/identity policy:** approve and implement the non-reuse, retention-bounded gate-removal mechanism and legacy NULL-owner reconciliation; prove delayed inserts cannot pass after orphan tombstone removal. Review any ADR-006/003 change explicitly.
5. **D6 — Isolated drill and review:** test the matrix above against non-production PostgreSQL, Queue, Worker and R2 with controlled pauses and crash points; capture provider behavior, security/CRA/GDPR evidence, retention/backup handling and operator runbooks. Only a separately authorized rollout may enable deletion.

Acceptance requires an exhaustive inventory of all R2 writers/credentials and SQL write paths, atomic same-key provider conditions, no unguarded old deployment or in-flight write for a completed identity, proven guard creation resolution, no deleted personal data reappearing after completion, and no UUID reuse after tombstone removal. Any failed proof leaves the gate closed and deletion unresolved. R2 conditional writes, extra marker objects, S3 credentials if needed, retained gate state and operator evidence add security/privacy/cost surface; quantify and approve these before rollout. No legal conformity or production-readiness claim is made here.

## Open decisions requiring approval

- Confirm the chosen Cloudflare API's atomic `If-Match` semantics for **Workers binding** or approve the S3 conditional API and its narrowly scoped server-only credential. Verify ETag behavior and guard/seal failure responses with provider documentation plus an isolated concurrency drill.
- Approve ADR-003/005 clarification for a temporary guard/seal at fixed private keys without permitting payload overwrite or changing deterministic result bytes. If that amendment is rejected, choose and prove another provider-enforced write fence; database-only barriers cannot satisfy ADR-006.
- Define how to conclusively settle uncertain initial guard creation and legacy unconditional PUTs. Without provider evidence, no finite wait, HEAD sequence or operator assertion establishes the required guarantee; affected deletion remains unresolved.
- Resolve global race-UUID non-reuse, safe orphan-tombstone and gate removal, account UUID reactivation prevention and justified retention. This may require an explicit ADR-006/003 amendment; indefinite pseudonymous denylist retention is not approved.
- Approve exact operator workflow, storage/backup retention, deletion of minimized gate/marker records, R2 key/metadata privacy, extra request/cost budget and handling of any lawful-retention exception. Neither review nor retry exhaustion counts as deletion success.
